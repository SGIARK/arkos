# TIER 1 · NOW

## Conversation A · The event vocabulary

These rows are persisted forever. A missing kind is not a bug you patch later,
it is every session written before you noticed.

### G22 · MISSING: no event kind for human messages

**Finding.** The vocabulary (`contracts.md:32-40`) has seven kinds and none is the
human's text. `content{text}` is defined as "model's text". `schema.md:75-77`
lists nine legal `kind` values, none of them `user`. Yet `contracts.md:206` says
`POST /sessions/{id}/messages` is "appended as user event, read next hop",
`decision_tables.md:24` says a log tail of "user message" loads as-is, and
`runner.wake()` folds events into messages (`contracts.md:191`). There is nothing
to fold. Human input is unrepresentable in the only durable store (D3), so every
attended conversation loses the user's half on reload.

**Resolution.** Add `user{text, source}` to the vocabulary and the `kind` list.
`source in {human, system}` so the nudge (`contracts.md:239`) and the lease and
status injections have a home too. The fold maps it to `role: "user"`.

**Self-critique.** The strongest objection: `content{text}` could carry a `role`
field, keeping the vocabulary at seven. It fails because `content` is the
streamed-token event, and streaming semantics (partial deltas, coalescing) do not
apply to a message that arrives whole. Overloading it makes the renderer branch on
a field inside a kind, which is the ad-hoc dict shape `events.py` exists to kill.

**Lands in.** contracts.md event vocabulary; schema.md `session_events.kind`.
**Confidence:** high

### G33 · MISSING: reasoning deltas have no representation, so the UI freezes during `<think>`

**Finding.** D25 turns thinking on. The client contract is
`Delta = text_delta | tool_call_delta | finish{usage}` (`contracts.md:256`).
`reasoning_content` matches none of them, so it is silently dropped. Qwen3
reasoning blocks routinely run hundreds of tokens, during which the loop yields
nothing and the UI shows nothing, and no `status{label}` is emitted because nobody
emits it. The headline metric is "first token < 1s" and
`test_streaming_first_token` uses a mocked model (`contracts.md:416`), so it
passes green while production stalls.

**Resolution.** Add `reasoning_delta` to `Delta`. The loop emits one
`status{label:"thinking"}` on the first reasoning delta of a hop and drops the
rest. No new event kind, no storage cost, no frozen screen.

**Self-critique.** Dropping reasoning content loses debugging value. That is the
right trade: reasoning text is model scratch, not transcript, and `session_events`
is never pruned. Storing think blocks forever in the audit table is the wrong
default. If it is needed, it belongs in `system_events`, pruned at 30 days.

**Lands in.** contracts.md model_module contract; decisions.md D25; Task 0a.
**Confidence:** high

### G40 · CONTRADICTION: the "final" vocabulary is missing two kinds, and `status` has no url field

**Finding.** The table headed "Event vocabulary (final)" lists seven kinds.
`schema.md:75-77` lists nine, adding `lifecycle` and `view_transform`. Both extras
are mandated elsewhere (`contracts.md:72`, `contracts.md:119-120`). Neither has a
defined payload, and the frontend switches on `event.type`, so `lifecycle` renders
as a generic row despite being what the status pill needs. Separately,
`status{label}` has one field, but four passages say it carries the browser stream
URL. A label cannot carry a URL.

**Resolution.** Add both rows with payloads: `lifecycle{from, to, reason}` and
`view_transform{rung, dropped_refs[]}`. Change `status{label}` to
`status{label, url?}`, url ephemeral and never replayed. Drop the word "final" or
make the table complete.

**Self-critique.** A `url` on `status` leaks a mount point into a durable table.
The stream endpoint is ownership-checked and cookie-authed, so a stale url grants
nothing; it 404s. The alternative, a `browser_available` kind, adds a kind for one
use when the design is trying to hold at seven.

**Lands in.** contracts.md event vocabulary.
**Confidence:** high

## Conversation B · The lifecycle does not close

Six gaps, one problem. The status column is in the DB, the grid, and
`/attention`, so it is three surfaces deep by the time you find out.

### G23 · CONTRADICTION: an attended turn end maps `done{completed}` to two statuses

**Finding.** `decision_tables.md:41`: text only, attended, `done{completed}` goes
to `idle`. The lifecycle table says `running -> completed` on `done{completed}`
(`contracts.md:84`) and `running -> idle` on "attended turn ended" with no event
named (`contracts.md:81`). `terminal_reason` is `done.reason` verbatim
(`contracts.md:90-92`). So an attended chat reply either writes `completed` plus
`ended_at` on a session that is alive, or the runner reads `mode` and overrides
the event, which puts interpretation back on the lifecycle path D26 exists to keep
off it. That row has no trigger.

**Resolution.** Add `turn_end` to `done.reason`. `done{turn_end}` is the only
trigger for `running -> idle`, and it is non-terminal: `terminal_reason` and
`ended_at` stay NULL. `finish_task` in attended mode still yields
`done{completed}` if the model calls it.

**Self-critique.** An event named `done` should mean the run is over, so a
non-terminal reason contradicts the name. That is a naming cost, not a design
cost, and it is cheaper than the runner reinterpreting the model's terminal event.
If the name grates, rename the event `end{reason}`. The mapping is what matters.

**Lands in.** contracts.md event + lifecycle tables; decision_tables.md §2.
**Confidence:** high

### G24 · CONTRADICTION: worker death requeues in one doc and fails in two others

**Finding.** `contracts.md:88`: `running -> pending`, "lease expired; sweep
requeues". D16 and `decision_tables.md:13-15`: a session caught mid-run becomes
`failed{interrupted}`, no auto-resume. Opposite policies for the same event. The
code sides with contracts: `harness_module/task_runner.py:247-265` respawns
everything in `running` or `awaiting_approval` at startup. Separately
`interrupted` is not in the `done.reason` enum (`contracts.md:42`), so
`failed{interrupted}` writes a value the contract forbids.

**Resolution.** D16 wins for v1. Delete the `running -> pending` row and re-add it
when Task 13 lands real leasing. Add `interrupted` to the enum. The startup sweep
synthesizes `done{interrupted}` before the transition, so "done owns
terminal-from-running" stays true and the transcript says why it stopped.

**Self-critique.** A requeue is strictly better for a task that died at 5 percent.
It does not survive: a blind requeue re-executes an unclosed side effect.
`decision_tables.md:23` is explicit that a dangling tool_call means "outcome
unknown, verify before retrying". Requeue is safe only once verify-on-wake is
proven, which is Task 13's problem.

**Lands in.** contracts.md lifecycle table + reason enum; decision_tables.md §1.
**Confidence:** high

### G25 · MISSING: nothing leaves a terminal status

**Finding.** The lifecycle table has no row whose `from` is `completed`, `failed`,
or `cancelled`. But D5 promises "the session you chat with is the one you reopen"
and the detail window IS the chat window. After the first unattended run finishes,
the user types, the event appends, and nothing ever runs. Compounding it,
`decision_tables.md:51` says an unattended `done{...}` goes `idle`, contradicting
`contracts.md:84-85` and `contracts.md:96`.

**Resolution.** Two edits. Fix `decision_tables.md:51`: an unattended `done{...}`
sets the terminal status and flips `mode` back to attended. Add one row,
`completed|failed|cancelled -> running`, trigger "human sends a message on a
terminal session", clearing `terminal_reason` and `ended_at`.

**Self-critique.** This makes "terminal" a lie and corrupts the operator index.
It survives: D3 says the log is the only durable truth and the `done{...}` event
stays there forever. The row is a current-state cache, not history. The
alternative, refusing messages on terminal sessions, reintroduces `create_session`
by the back door and breaks the one-transcript promise D5 paid for.

**Lands in.** contracts.md lifecycle table; decision_tables.md §2b.
**Confidence:** high · **See escalation E1.**

### G26 · MISSING: a session waiting on a lease has no status, no trigger, no waker

**Finding.** `decision_tables.md:100` and `contracts.md:334-336` both say a
contended session "parks as waiting". There is no `waiting` status, the only park
transition is `running -> awaiting_approval` triggered by a park tool, and the only
way back is the respond endpoint. Using `awaiting_approval` turns the dot ochre and
puts a phantom row in `/attention`, the opposite of D26. "A lease-wait timeout
parks rather than fails" is circular: it parks into a state that does not exist.

**Resolution.** A lease wait is not a park. The session stays `running` and emits
`status{label:"waiting for the sandbox"}`, which is what `status` exists for. The
wall clock excludes lease-wait time using the same active-segment accounting park
already needs. On timeout the tool returns
`ResultEnvelope{ok:false, error_kind:timeout, retryable:true}` and the model routes
around it. Delete both "parks as waiting" sentences.

**Self-critique.** Staying `running` while doing nothing makes the green dot lie.
It does not: green means working, and waiting on your own other session's sandbox
is working. No hops burn, because no model call happens. The stronger objection is
that an in-process asyncio wait breaks under multi-worker. True, and that is Task
13; for v1 (one event loop, D11) an asyncio condition plus the DB row as durable
record is correct, and the timeout envelope degrades safely.

**Lands in.** contracts.md resource contract; decision_tables.md §7.
**Confidence:** high

### G28 · MISSING: the approve endpoint has no lifecycle row, and `mode` has no writer

**Finding.** `POST /sessions/{id}/approve` is "202, attended -> unattended; the run
begins" (`contracts.md:215`). The session is `idle` then. The only trigger for
`idle -> running` is "human sends a message", and approve is not a message. The
table is missing a row for the single most consequential command in the product,
the one that hands the model autonomy. Separately `mode` flips twice per run, and
`contracts.md:90` names `transition()` the sole writer of `status` while naming
nothing as the writer of `mode`.

**Resolution.** Add the row: `idle -> running`, trigger `POST
/sessions/{id}/approve`. Widen the signature to
`transition(session_id, expected, new, reason, mode=None) -> bool` so status and
mode move in one conditional UPDATE. A mode flip without a status change is
illegal; both mode flips already change status.

**Self-critique.** Mode is not status and does not belong in the FSM writer. It
belongs anyway: D22's guard rail is "every state must change what a person sees",
and mode changes what a person sees. Coupling the writes also removes the window
where a session is unattended for budget accounting but still recorded attended.

**Lands in.** contracts.md lifecycle table and `lifecycle.py` signature.
**Confidence:** high

### G54 · CONTRADICTION: "done is the ONLY thing allowed to change status" is false six times

**Finding.** `contracts.md:40` says `done{reason}` is "the ONLY thing allowed to
change task status". The transition table on the same page lists six transitions
with no `done` event: create, lease claim, human message, park, respond, and
cancel from three states. `contracts.md:90` states the correct narrower rule.

**Resolution.** Change the cell to "run over; the only writer of a terminal status
from `running`". One line.

**Self-critique.** Obvious shorthand nobody would misread. Someone would: it sits
in the first normative table in the doc, and it is the kind of absolute a reviewer
cites to reject a PR that writes `cancelled` from the cancel endpoint, which
`decision_tables.md:91` requires.

**Lands in.** contracts.md event vocabulary table.
**Confidence:** high

### G30 · MISSING: shared (no-auth) MCP connections have nowhere to live under D24

**Finding.** D24 deletes `_user_conn_id()` and `_shared_conn_id()`. The only
replacement store is `user_connections`, whose `user_id` is
`not null references users(id)` with PK `(user_id, mcp_url)`. Shared servers have
no user. They exist and are load-bearing: `config.yaml:85-90` configures Slack with
`requires_auth: false` and a bot token, and `smithery.py:343-344` mints its id via
`_shared_conn_id()`, called from `initialize_servers()`. Delete the formula with no
row to replace it and every restart mints a fresh connection for every shared
server, which is the exact stranding D24 exists to prevent, and Task 3's test is
unpassable for shared servers.

**Resolution.** Add `shared_connections {mcp_url pk, connection_id, status,
tools_cache, refreshed_at}` to migration 0. Same mint-and-store rule, one row per
shared server, no user column.

**Self-critique.** A second table duplicates the first; a sentinel user row would
do. A sentinel is worse: it puts a fake row in `users` and every ownership check
has to special-case it. The other objection, delete shared servers entirely,
breaks Slack, whose credential is a workspace bot token. That also raises a trust
question auth.md does not currently cover: every user's agent acts as the same bot
identity.

**Lands in.** schema.md; contracts.md fate map; auth.md trust boundaries.
**Confidence:** high

### G31 · UNDERSPEC: `connection_id` mint-and-store ordering reopens the drift D24 kills

**Finding.** `contracts.md:61` says the id is "issued once at connect and STORED".
Neither doc says who generates it or in what order relative to the Smithery call.
The code shows Smithery does not issue it: the id is a path segment we choose
(`smithery.py:128`). So we mint, then PUT. If the PUT succeeds and the INSERT
fails, the next attempt mints a different id and the old connection is stranded
holding the user's live OAuth grant. Same failure mode D24 was written to
eliminate, moved from rename-time to crash-time.

**Resolution.** Write the row first. Mint a UUID, INSERT with `status='pending'`,
then PUT, then UPDATE from Smithery's response. A crash leaves a pending row whose
id is reused on retry, so the id is stable across every failure. Say "we mint it,
Smithery accepts it" in D24 so nobody re-derives it later.

**Self-critique.** A pending row for a connection that never completed is garbage.
It is cheap garbage, one row per user per server, reused on the next attempt, and
it is the only way to make the id survive a crash. The alternative, hashing
`(user_id, mcp_url)`, is the formula D24 deleted.

**Lands in.** decisions.md D24; contracts.md fate map.
**Confidence:** medium

### G46 · MISSING: migration 0 drops the columns the approval reminder used

**Finding.** Task 6 promises "reminder at 1h". No doc says through what. The
existing channel is a Slack DM: `state_approval.py:29` imports `send_dm`,
`slack_notify.py:25` reads `users.slack_user_id`, `harness_module/users.py:112-127`
sets it. Migration 0's `users` is `{id, email, created_at}`, so `slack_user_id`,
`username`, and `last_seen` disappear with no successor and no fate-map mention.
The DM also links to `config.get("app.public_url")`, a key read by code and absent
from config. So an unattended run parks and the human is notified by nothing.

**Resolution.** Decide the channel in `contracts.md`. Cheapest correct answer for
v1 is email, since `users.email` is already in migration 0 and Supabase supplies
it, sent by a sweep over unanswered approvals older than an hour. Add
`app.public_url` to the config block. If Slack DMs are wanted, `slack_user_id` has
to go back into migration 0.

**Self-critique.** Notification is polish, not spine. It is spine for unattended
runs: D5's whole value is that the session runs without you, and a park nobody
learns about turns a 30-minute task into an indefinite one. Adding email is scope
creep, fairly said; the minimum acceptable alternative is deleting "reminder at 1h"
from Task 6 rather than leaving an undeliverable promise.

**Lands in.** contracts.md; schema.md `users`; spec Task 6.
**Confidence:** medium
**RESOLVED 2026-08-17 (owner): the reminder is cut, not given a channel.** The
minimum alternative this entry names is the one taken. There is no mailer in the
repo and adding one is a feature with its own spec. Staleness is carried by the

as the review reply on the same question recommended. `users.email` stays for

### G47 · MISSING: `project_files.storage_path` names no backend

**Finding.** `schema.md:38` is `storage_path text not null, -- durable store;
mounted into sandbox`. No doc names the store: not Supabase Storage, not S3, not
local disk, not the e2b filesystem. `looking_glass_spec.md:157-159` flags
sync-back as undesigned while LG-2's own test requires "upload a file, task reads
it from its sandbox".

**Resolution.** Name it: Supabase Storage, one bucket, path
`{user_id}/{project_id}/{file_id}`, because Supabase is already the DB and the
auth provider. Upload writes storage then the row. Mount is a copy into the
sandbox at lease acquisition, not a live mount, because e2b has no network
filesystem. Sync-back stays out of v1: sandbox files become project files only via
an explicit `save_file` tool. That answers open question 2 without a
conflict-resolution design.

**Self-critique.** An explicit `save_file` relies on the model calling it, which is
D15's known failure mode with `finish_task`. Accepted, and still better than the
alternatives: sync on every write races a mid-run upload with no conflict rule, and
sync at `finish_task` silently loses everything from a run that fails.

**Lands in.** schema.md `project_files`; looking_glass_spec.md open question 2.
**Confidence:** medium

## Conversation D · Deployment shape

### G35 · RISK: SameSite=Lax plus a cross-origin EventSource sends no cookie

**Finding.** The auth design is httpOnly + Secure + SameSite=Lax.
`auth.md:47` justifies it with "in production the frontend is same-origin".
`contracts.md:219` simultaneously says "CORS is pinned to the real origin with
credentials allowed", which is only meaningful if the frontend is a different
origin. Both cannot be true. If app and API are cross-site, SameSite=Lax sends the
cookie only on top-level GET navigations, so `EventSource` (a subresource request)
gets no cookie and both SSE streams 401 on every connect. `test_cookie_session`
asserts that a missing or foreign cookie is rejected, which passes while the real
browser is also rejected.

**Resolution.** Make same-site a stated deployment requirement, not an aside:
`/app` and the API served from one origin behind Caddy; CORS then unnecessary and
`allow_origins` set to the single app origin as defence-in-depth. Say in `auth.md`
that a cross-site frontend requires SameSite=None plus explicit CSRF tokens and
that we are not doing that. Add `withCredentials: true` on `EventSource`
regardless, since it costs nothing and fails closed.

**Self-critique.** This is an infra note, not a contract. It is a contract:
`contracts.md:216-220` is the auth line for every endpoint in the table and
`auth.md` gate 2 is a release blocker. Getting the site relationship wrong means
the entire push architecture silently does not work in production, and it is
invisible in tests.

**Lands in.** auth.md session cookie section; contracts.md auth paragraph.
**Confidence:** high · **See escalation E2.**

## Before Task 2 (the loop)

**G43 · UNDERSPEC: `ctx` and `source` are undefined.** `execute(name, args, ctx)`
appears once and `ctx` is never defined in any of the seven docs. It must carry
user_id, session_id, project_id, lease handles, and the cancel token. `source` is
never enumerated. **Fix:** `ToolCtx{user_id, session_id, project_id, mode, leases,
cancel_token}` as a frozen dataclass built once per `run_turn`; `source in
{interactive, background}` mapped one-to-one from `mode`. The reason this matters is
narrow and important: if `ctx` carries a DB connection, `tool_module` becomes a
second writer to `session_events` and the single-funnel invariant quietly dies. *high*

**G44 · MISSING: the system prompt and nudge have no owner; the manifest breaks
replay determinism.** Four passages depend on a system prompt. No file owns it, no
config key holds it, and it necessarily differs by mode. The nudge text has no home.
Separately `contracts.md:121-122` claims assembly is "deterministic given (log,
config)" while the request also contains `manifest(user_id)`, which changes when a
user connects a server. **Fix:** prompts in `agent_module/prompts/` as functions, one
per mode plus the nudge; restate determinism as "(log, config, manifest)"; snapshot
the manifest tool-name list into the session's first event. *high*

**G38 · UNDERSPEC: `requires_approval` has no enforcement path.** The contract says
only "checked at execute time", but `execute()` never raises, so a check there can
only return an envelope, and no `error_kind` fits. Nothing says whether the loop
parks or who writes the `approvals` row. Meanwhile `auth.md:78-80` makes this the
primary prompt-injection mitigation. A security control with no enforcement path is
not a control. **Fix:** enforce in the loop before dispatch, reusing the identical
park mechanism `request_approval` already has; in attended mode the human is present
so the call proceeds. Default `requires_approval=true` for every `mcp_*` tool not on
a read-only allowlist. That default makes unattended runs expensive, which is the
point: the alternative is the control being off by default forever. *high*

**G49 · UNDERSPEC: `hops_used` has two sources of truth.** Contract says hops are
counted from the log; `schema.md:59` stores a column. Neither wins. Budget keys are
`interactive`/`worker` while the mode enum is `attended`/`unattended`, with no
mapping written down. `hops_max` is returned by the API and stored nowhere. **Fix:**
log authoritative, column is a cache written in the same transaction as the `budget`
event; rename the budget keys to match the mode enum; derive `hops_max` at read time.
Two names for one axis is how `session_id` versus `task_id` happened. *medium*

## Before Task 3 (tools)

**G42 · UNDERSPEC: `clearable_tools` names a tool that does not exist.** The rung 1
whitelist is `[read_file, grep, glob, list_dir, search]`. `search` is not in the
manifest. Worse, it excludes the two largest producers of context pressure,
`browser_task` results and every `mcp_*` result, so the one v1 recovery rung cannot
clear what actually causes overflow. The "drop re-derivable" framing is also wrong
for the case that matters: `browser_task` is not re-derivable, the web moved.
**Fix:** delete the whitelist. Blob every result over a floor at append time, and
have rung 1 clear the oldest blobbed results regardless of producer. Nothing is lost
because the blob is durable and `read_result` already exists. Config keeps one key. *medium*

# ESCALATIONS

Three real either/ors, each with a genuine trade-off.

### E1 · Does an unattended run end terminal, or end `idle`?

Related to G23 and G25. The docs say both.

- **Terminal (`completed`).** The grid dims, the operator index works,
  `terminal_reason` and `ended_at` mean something. Cost: continuing the
  conversation needs a `terminal -> running` transition, so "terminal" is
  reopenable and the row's history is lossy. The log still has it.
- **`idle`.** Matches D5's one-session story exactly. Cost: no session ever reaches
  a terminal state through the normal path, the operator index never fills, the grid
  never dims, and "terminals come from unattended runs" becomes false.

Recommendation: terminal plus a reopen transition. This changes what the grid
means, so it is yours.

### E2 · Is `/app` same-site with the API, or do we pay for SameSite=None?

Related to G35. The docs assert both a same-origin frontend and pinned CORS with
credentials. **This one decides whether SSE authenticates at all**, so it blocks
Tier 1.

- **Same-site behind one Caddy origin.** Lax works, EventSource works, CORS is
  decoration, CSRF handled by Lax plus the origin check. Cost: a deployment
  constraint, and a future CLI or mobile client needs bearer alongside (already
  anticipated in auth.md).
- **Cross-site with SameSite=None.** Frontend lives anywhere. Cost: full CSRF
  surface, so the origin check stops being defence-in-depth and becomes the only
  control, and every SSE connection needs `withCredentials` plus exact-origin CORS.

### E3 · Does D26's "every open question glows ochre" survive contact with an 8B?

D26 makes every unanswered question mark its project ochre, turning the grid into a
complete waiting-on-me inbox. A chatty 8B in attended mode asks questions
constantly, and each one lights the grid. Recommendation: redefine ochre as "a park
is open", so an attended chat question shows in the session but does not colour the
project. That narrows D26 rather than reversing it, and keeps the grid honest as a
background-work monitor.
