1. SYMPTOM: THE NEW FRONTEND ISN'T SURFACING TASKS
--------------------------------------------------------------------------------

USER:
The old frontend had only MCP; we recently added computer use through an E2B
filesystem. The original MCP flow was: send a request, buddy makes a plan, the
user approves the plan, a subagent spawns and appears in the task list, the
subagent requests approval (which shows in the approval window), and when it
finishes a "done" message appears in the approval window. This is now broken for
both the original MCP flow and the computer-use flow: tasks aren't reaching the
task list, and we can't see what the agent is doing. Please diagnose the problem;
don't write any code.

ASSISTANT:
Mapped the full task/approval pipeline end to end. Source is largely coherent and
unit tests pass, so the breakage is at integration boundaries. Four defects plus
one deployment risk:

  1. The frontend hides everything that goes wrong. It polls only
     status=running and status=awaiting_approval, never completed/failed, and
     every fetch wrapper swallows errors. A task that fails fast or sticks in
     "pending" never appears, and server 500s are invisible.
  2. Executor subagents fail instantly on any error: agent.py's error path sets
     current_state to "agent_reply", a buddy-only state that doesn't exist in the
     executor graph, raising KeyError so the task is marked failed.
  3. Executor can never call MCP tools: ScopedToolManager.list_all_tools() took no
     user_id, but the executor called it with one, raising TypeError that degraded
     every step to "ask the human."
  4. agent.py error path crashes as in (2).
  5. Migrations are manual; if the unified schema wasn't applied, every query 500s,
     and (1) hides it.

11. GLOBAL STATE AUDIT (RACE CONDITIONS)
--------------------------------------------------------------------------------

USER:
I thought the prompt was per-user. What is global that should be per-user? I'm
looking for race conditions, as outlined in ISSUES.md.

ASSISTANT:
The prompt is per-user now. What remains:
  1. The module globals for the system prompt and tool list, rewritten on every
     chat request — a cross-user write race and redundant work.
  2. The agent is handed the global shared-only tool dict, not the per-user set.
  3. The shared tool-manager's per-user dicts are mutated across awaits — a
     same-user race.
  4. The single shared StateHandler holds shared State instances — safe only while
     states stay stateless.
  5. The per-user Memory object is shared across a user's concurrent requests.
The identity-keyspace mismatch from ISSUES.md is largely resolved; every endpoint
now derives identity from the verified token.

12. FIXES 1, 4, AND 5 (and a confirmed memory bleed)
--------------------------------------------------------------------------------

USER:
How do we fix items 1, 4, and 5? I think I've seen memory bleed.

ASSISTANT:
Implemented and verified all three:
  - Fix 1: Removed the per-request global prompt rebuild and all its call sites.
    The prompt is already assembled per-user, so the global rewrite was pure race
    surface plus an extra round trip per message.
  - Fix 4: State objects now freeze after construction, and the handler freezes
